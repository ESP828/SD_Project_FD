# foodduck DB 테이블별 상세 분석

DB `foodduck` (MySQL 8.0.45) 의 전체 33개 도메인 테이블(+시스템 테이블 1개)을 개별 분석합니다.
전체 구성/ERD는 [001-01. DB 테이블 구성도.md](./001-01.%20DB%20테이블%20구성도.md) 참고.

---

## account — 계정 (Row: 38)

**역할**: 서비스의 모든 사용자 계정(일반/사업자/관리자 공용)의 핵심 테이블.

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|
| account_id | bigint unsigned PK, AI | N | - | |
| login_id | varchar(50) UNIQUE | Y | - | 일반 로그인 아이디 |
| email | varchar(100) UNIQUE | N | - | |
| nickname | varchar(30) UNIQUE | N | - | |
| gender | enum(UNSPECIFIED,MALE,FEMALE,OTHER) | N | UNSPECIFIED | |
| birth_date | date | Y | - | |
| profile_image_url | varchar(500) | Y | - | |
| email_verified | tinyint(1) | N | 0 | |
| profile_completed | tinyint(1) | N | 0 | |
| status | enum(ACTIVE,INACTIVE,SUSPENDED,WITHDRAWN) | N | ACTIVE | 인덱스(idx_account_status) |
| last_login_at | datetime(6) | Y | - | |
| created_at / updated_at | datetime | N | CURRENT_TIMESTAMP | |
| deleted_at | datetime(6) | Y | - | 소프트 삭제 |
| password | varchar(255) | N | - | |
| provider | varchar(20) | N | - | |
| provider_id | varchar(50) | Y | - | |
| role | varchar(20) | N | - | |
| username | varchar(50) | N | - | |

**키/인덱스**: PK(account_id), UNIQUE(nickname/email/login_id), INDEX(status)

**분석/특이사항**:
- `password`/`provider`/`provider_id`/`role`/`username` 컬럼이 `account` 테이블에 직접 있는데, 별도로 `account_credential`(비밀번호 해시 전용)과 `social_account`(소셜 로그인 연결) 테이블도 존재한다. 즉 **인증 정보가 이중으로 관리**되고 있는 것으로 보인다 — 초기 설계(단일 테이블)에서 정규화된 `account_credential`/`social_account`로 리팩터링하는 과도기이거나, `account.password`/`provider`가 레거시 컬럼일 가능성이 있다. 실제 서비스 코드에서 어느 쪽을 쓰는지 확인이 필요하다.
- `role`이 문자열(varchar)로 관리되는데 별도 `authority`/`account_authority` 테이블도 존재 — 권한 체계 역시 두 가지 메커니즘(role 컬럼 vs RBAC 매핑 테이블)이 공존한다.
- `deleted_at`과 `status='WITHDRAWN'`이 함께 있어 탈퇴 처리 방식이 컬럼 2개로 표현됨 (일관성 확인 필요).

## account_authority — 계정-권한 매핑 (Row: 39)

**역할**: `account` ↔ `authority` N:M 매핑 (RBAC).

| 컬럼 | 타입 | NULL | 기본값 |
|---|---|---|---|
| account_id | bigint unsigned PK, FK→account | N | - |
| authority_id | smallint unsigned PK, FK→authority | N | 0 |
| created_at | datetime(6) | N | CURRENT_TIMESTAMP(6) |

**FK**: account_id→account(CASCADE), authority_id→authority(RESTRICT)
**분석**: 복합 PK로 중복 부여 방지. account가 삭제되면 매핑도 자동 삭제(CASCADE), authority는 사용 중이면 삭제 불가(RESTRICT).

## 종합 소견

1. **핵심 중복/정리 후보**:
   - `email_verification` vs `signup_email_verification` (해시 저장 vs 평문 저장, 목적 중복)
   - `favorite` vs `preset`(name=NULL인 기본 리스트) (찜 기능의 이중 구현)
   - `account.password/provider/role` vs `account_credential`/`social_account`/`account_authority` (인증·권한 정보의 이중 관리)
2. **현재 데이터 상태**: 도메인 데이터는 대부분 개발/테스트 초기 단계(0~수십 건)이며, `public_restaurant`만 공공데이터 시드로 82만 건 이상 적재되어 있다.
3. **인코딩 이슈**: `public_restaurant` 테이블/일부 컬럼의 COMMENT가 깨져 있음 — 데이터 값 자체는 별도 검증 필요, DDL 재작성 시 세션 charset(`utf8mb4`)을 명시할 것을 권장.
4. **잘 지켜진 설계 원칙**: 소프트 삭제, CHECK 제약을 통한 XOR(단일 소스) 강제, 해시 기반 토큰/비밀번호 저장, 부분 유니크 제약 트릭 등 전반적으로 견고한 스키마 설계가 확인된다.
