# Flyway 이력과 실제 DB 불일치 진단 및 preset_image 테이블 생성

Presset 이미지 첨부 기능 작업 중 `GET /api/presets`가 500 에러를 내는 문제와, `FLYWAY_ENABLED=true`로 서버를 재기동했을 때 발생한 마이그레이션 검증 실패를 진단하고 해결한 기록입니다.

---

## 증상

1. Presset 목록/상세 조회(`GET /api/presets`, `GET /api/presets/{id}`)가 500 에러를 반환.
2. 서버를 `FLYWAY_ENABLED=true`로 재기동하면 아래 에러로 애플리케이션 기동 자체가 실패:
   ```
   FlywayValidateException: Validate failed: Migrations have failed validation
   Detected resolved migration not applied to database: 4.1.
   ```

## 원인 진단

읽기 전용으로 실제 DB(`jdbc:mysql://192.168.1.185:3306/foodduck`)를 직접 조회해 확인함 (JDBC로 임시 조회 프로그램 작성, MySQL 클라이언트 미설치 환경이라 우회).

### 1) `flyway_schema_history` 실제 내용

| version | description | success | installed_on |
|---|---|---|---|
| 4 | `<< Flyway Baseline >>` | true | 2026-08-04 |
| 5 | public restaurant search fulltext | true | 2026-08-05 |
| 6 | add business application opened at | true | 2026-08-05 |

- 이력이 **V6에서 멈춰 있음**. `V4.1`, `V8`, `V9`, `V10`, `V11`, `V12`는 이력에 전혀 없음.
- `V4.1`은 baseline(V4)과 V5 "사이" 버전이라, 이미 V5·V6이 적용된 이력 위에서는 "순서가 어긋난 gap"으로 인식되어 Flyway가 검증을 거부함. 반면 V8 이상은 단순히 "아직 실행 안 한 최신 마이그레이션"이라 검증 에러를 일으키지 않음(그래서 에러 메시지에 4.1만 언급됨).

### 2) 실제 테이블 존재 여부 (정보 스키마 직접 조회)

| 테이블 | 존재 여부 |
|---|---|
| `public_restaurant` (V4.1) | ✅ 존재 |
| `preset_restaurant` (V8) | ✅ 존재 |
| `preset_tag` (V9) | ✅ 존재 |
| `preset_favorite` (V9) | ✅ 존재 |
| `review.public_restaurant_id` (V10) | ✅ 존재 |
| `preset_image` (V12) | ❌ **없음** |

`preset` 테이블은 여전히 `summary`, `description`, `image_url`, `name` 컬럼을 갖고 있음 → **V11(컬럼 삭제)도 아직 미적용** (다만 코드가 더 이상 이 컬럼들을 참조하지 않아 당장 에러를 일으키지는 않음).

### 결론

**이 프로젝트는 Flyway를 한 번도 실제로 끝까지 실행한 적이 없고, 매번 마이그레이션 SQL 파일만 저장소에 남겨두고 실제 적용은 DBeaver 등으로 수동 DDL 실행해온 방식**이다. `application.properties`의 다음 주석이 이를 뒷받침한다.

```properties
# 기존 DB에 V1을 잘못 적용하지 않도록 기본 비활성화한다.
# 비어 있는 새 DB에 설치할 때만 FLYWAY_ENABLED=true로 실행한다.
spring.flyway.enabled=${FLYWAY_ENABLED:false}
```

`V4.1__create_public_restaurant_table.sql` 파일 자체에도 동일한 취지의 주석이 있음:

> 원래는 Flyway 없이(개발 초기 ddl-auto=update 시절) 만들어져 있던 테이블이라 마이그레이션에 빠져 있었다.

즉 `outOfOrder=true`나 이력 조작으로 Flyway 검증을 억지로 통과시키려 하면, 이미 존재하는 테이블을 다시 CREATE 시도하다 실패하거나(V4.1, V8~V10) 예상치 못한 부작용이 날 위험이 컸다. **Flyway를 켜는 것 자체가 이 문제의 올바른 해법이 아니었다.**

## 해결

Flyway는 손대지 않고(계속 비활성 상태 유지), **`preset_image` 테이블만 V12 마이그레이션 파일 내용 그대로 직접 CREATE TABLE**로 생성함 — 이 프로젝트의 기존 운영 방식과 동일한 방법.

```sql
CREATE TABLE preset_image (
    preset_image_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    preset_id BIGINT UNSIGNED NOT NULL,
    stored_filename VARCHAR(255) NOT NULL,
    original_filename VARCHAR(255) NULL,
    content_type VARCHAR(100) NOT NULL,
    file_size BIGINT UNSIGNED NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (preset_image_id),
    UNIQUE KEY uq_preset_image_preset (preset_id),
    CONSTRAINT fk_preset_image_preset
        FOREIGN KEY (preset_id) REFERENCES preset (preset_id) ON DELETE CASCADE
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci
  COMMENT='프리셋 대표 이미지 파일 메타데이터';
```

적용 후 `GET /api/presets`가 200으로 정상 응답하며, 기존 Presset 2건(`성수`, `ddd`)도 삭제되지 않고 그대로 유지된 것을 확인함 — **애초에 데이터가 삭제된 적은 없었고**, 목록이 안 보였던 건 조회 쿼리가 존재하지 않는 테이블을 참조하다 500 에러가 난 것이었음.

## 추가 진단 및 해결: Presset 신규 등록 500 오류

`preset_image` 생성으로 조회 API를 복구한 뒤에도 로그인 사용자의 `POST /api/presets`는 500을 반환했다. 실제 요청을 재현한 결과 인증, multipart 파싱 및 `PresetCreateRequest` 바인딩은 모두 정상적으로 통과했고, 저장 SQL에서 다음 MySQL 오류가 발생했다.

```text
SQL state [HY000]; error code [1364]
Field 'summary' doesn't have a default value
```

현재 `PresetQueryRepository.create()`는 최신 DTO에 맞춰 `title`, `category`, `account_id`, `is_public`만 저장하지만, 실제 개발 DB에는 V11이 반영되지 않아 `summary VARCHAR(255) NOT NULL` 컬럼이 기본값 없이 남아 있었다. H2 통합 테스트용 `schema.sql`에는 이미 이 컬럼이 제거되어 있어 테스트 9개가 통과했고, 이 차이가 실제 DB 장애를 숨기고 있었다.

기존 값을 복구할 수 있도록 다음 백업 테이블에 Presset 2건의 레거시 컬럼을 먼저 보존했다.

```sql
CREATE TABLE preset_legacy_content_backup_20260810 AS
SELECT preset_id, summary, description, image_url
FROM preset;
```

백업 행 수가 기존 `preset` 행 수와 같은 2건임을 확인한 후 V11과 동일하게 실제 개발 DB에 다음 DDL을 수동 적용했다.

```sql
ALTER TABLE preset
    DROP COLUMN summary,
    DROP COLUMN description,
    DROP COLUMN image_url;
```

적용 후 검증 결과:

- 기존 Presset 2건 유지
- 이미지 없는 로그인 사용자 등록: `201 Created`
- PNG 이미지가 있는 로그인 사용자 등록: `201 Created`
- `account_id`, `is_public`, `preset_image` 메타데이터 및 실제 이미지 파일 저장 확인
- 비회원 등록: `401 Unauthorized`
- 빈 제목/카테고리 등록: `400 Bad Request`
- 비공개 Presset: 비회원 `404`, 소유자 `200`
- 생성한 Presset 2건 모두 최신순 목록 노출 확인
- 검증용 Presset 2건과 업로드 이미지 파일은 확인 후 삭제하여 기존 데이터 2건만 유지
- `PresetControllerIntegrationTest`: 9개 성공

## 남은 이슈 (추후 확인 필요)

- `preset.name` 컬럼은 실제 DB에 남아 있지만 V11 제거 대상이 아니며 현재 Presset 등록·조회 코드에서 사용하지 않는다. 별도 요구사항과 데이터 의미를 확인하기 전에는 삭제하지 않는다.
- 레거시 값은 `preset_legacy_content_backup_20260810`에 보존되어 있다. 복구 필요가 없다고 확정되기 전에는 이 백업 테이블을 삭제하지 않는다.
- Flyway 이력이 V6에서 멈춰 있고 V8 이상 마이그레이션은 이력에 없는 상태가 계속 누적되고 있음. 당장 문제를 일으키지는 않지만, 언젠가 Flyway를 다시 정상 궤도에 올리려면 `flyway_schema_history`에 지금까지 수동 적용된 버전들을 baseline/repair로 정리하는 작업이 필요할 수 있음.
- 새 DB(운영 배포용 등)를 처음부터 세팅할 때는 이 프로젝트의 마이그레이션 파일들이 Flyway로 순서대로 정상 적용되는지 별도로 검증이 필요함(현재 개발 DB 기준으로는 검증되지 않은 경로).
